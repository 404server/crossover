\section{Introduction}
\label{sec:intro}

A team that runs an application on Kubernetes decides how to cut it into deployable units, and with that how a
fixed share of a node pool or a CPU quota is divided among processes. The argument for microservices is that a
decomposed system can give resources to the part that needs them. The argument against is that every remote call
costs time and CPU. Migrations in both directions keep the question open. The Prime Video team moved a monitoring
service from a distributed design into a single process and reported that this ``reduced our infrastructure cost
by over 90\%''~\cite{Kolny2023}, and Su et al.\ analyse four such moves back to a monolith~\cite{Su2024}.

The published comparisons agree more than they appear to. Where both styles run on the same hardware, the
monolith is mostly faster or equal; the microservice version comes out ahead when it receives more instances or
other resources (Section~\ref{sec:related}). What the comparisons rarely show is how large the gap is and where it comes from. Of the twelve we
review in Section~\ref{sec:related}, only two report a tail percentile, and most drive load with closed loops,
which slow down with the system they measure and so hide the tail~\cite{Schroeder2006,Tene2015}. None splits
end-to-end latency into the layers where distribution adds cost. Only one holds the resources of both styles equal throughout, and two more only in their local runs. This
matters because a microservice deployment of the same code runs more processes, each with its own runtime,
connection pools and share of the CPU. Reviews of the migration literature accordingly describe its results as
conflicting~\cite{Rodrigues2024} and note a lack of comparative studies~\cite{RodriguesJSS2025}.

This article reports a controlled comparison designed around those problems. It implements and executes a
measurement protocol we designed beforehand, and it revises that protocol where building it showed parts of it to be unsound. The testbed runs one e-commerce application in four topologies: a monolith (A), four
coarse-grained services (B), eight fine-grained services (C), and the same eight services with an Istio service
mesh (D). All four run the same binary with identical business code; only the mapping of modules to processes
differs. Every configuration receives the same CPU budget. Each process reports, in a W3C \texttt{Server-Timing}
header propagated through the call tree, how long it spent in application code, database calls, serialisation,
framework dispatch and waiting for its callees. This yields an exact per-request decomposition of end-to-end
latency without synchronised clocks. Latency is measured under open-loop load and capacity under closed-loop load, and the CPU counters
of every container give an operational bound that names each configuration's bottleneck.

The study answers four research questions:
\begin{description}
\item[RQ1] How much tail latency does decomposition add at low load, when every configuration has spare
capacity?
\item[RQ2] Under an equal resource budget, does any decomposed configuration reach a higher throughput than the
monolith, and if so, from what load on? Does the answer change when the budget is allocated in
proportion to demand, or when an autoscaler can add replicas up to a shared ceiling?
\item[RQ3] In which layers does the additional latency of decomposition arise, and what limits each
configuration's capacity?
\item[RQ4] How much does a sidecar service mesh add, and does its cost grow with the number of remote calls on a
request's path?
\end{description}
RQ1, RQ2 and RQ4 correspond to hypotheses H1--H3 of the protocol, each stated with an explicit falsification
condition (Section~\ref{sec:hypotheses}).

The contributions are:
\begin{enumerate}
\item a testbed in which configurations differ only in deployment topology: one binary whose modules are placed in
one process or several at deployment time, as in Service Weaver~\cite{Ghemawat2023}, run under an equal CPU budget
and checked for identical responses on every deployment;
\item a per-layer latency accounting that aggregates caller- and callee-side timings in-band, in one
\texttt{Server-Timing} header per hop, together with cgroup-level CPU and throttling data and an operational
bottleneck bound that explain the capacity limits;
\item measurements from \the\numexpr\xo{cells}+\xo{prop/cells}+\xo{work/cells}+\xo{workprop/cells}\relax{} fresh
deployments on a local cluster and \the\numexpr\xo{eks/cells}+\xo{hpa/cells}\relax{} on Amazon EKS, under an
equal, a demand-proportional and an autoscaled allocation and at two levels of service demand, analysed with the repetition as the unit of
replication. They test H1--H3 and put a price on each synchronous hop;
\item the software defaults that bias such comparisons and how the testbed neutralises them (Section~\ref{sec:discussion}),
and the testbed, campaign runner, raw data, analysis pipeline and an interactive dashboard, from which every number
in this article is generated.
\end{enumerate}

Section~\ref{sec:threats} discusses threats to validity, and Section~\ref{sec:conclusion} concludes.
